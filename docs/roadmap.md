# 整体规划与分阶段落地

**原则**：整体架构一次规划到位（尤其是数据模型，见 `memory-design.md` §7），但**验证和实现从单个用户开始**。群、路由、多租户的字段和过滤逻辑提前就位并测过，但不实现写入路径——避免"先做单用户、以后再加群"变成"回头给历史数据补作用域"。

---

## 整体架构

```
                    ┌──────────────────────────────────────┐
  workforce web ⇄ WS│            omni-server               │
   （语音/文字）     │                                      │
                    │  VoiceSession  ──────────────────────┼─⇄ DashScope Realtime
                    │   （解析事件、注入、合流）             │    （语音进语音出）
                    │        │                             │
                    │        ├─ MemoryStore （分层/作用域）  │
                    │        │                             │
                    │        └─ Sidecar ───────────────────┼─→ 快速文本模型
                    │            （查询/分析/知识库）        │    （qwen-turbo）
                    │                                      │
                    │  Extractor（会话结束时批量提炼）  ─────┼─→ 快速文本模型
                    └──────────────────────────────────────┘
                             │
                             └─→ App（结构化查询结果，语音说不出的东西界面来显示）
```

三条决定形状的约束：

1. **连接必须由服务端持有**。要在中间解析事件才能注入记忆和查询结果，所以不能让客户端直连上游。
2. **服务端要部署在 cn-beijing**。专属域名钉死在北京，部署远了每个音频包都白付一次跨区往返。
3. **工具不走 Realtime Function Calling**，走并排的文本模型。见 `memory-design.md` §9。

## 阶段划分

### 阶段 1：单用户跑通（本次已完成的部分 + 待实测）

**已完成**（代码 + 70 个离线测试）：

| 模块 | 内容 |
|---|---|
| `omni/layers.py` | 七层定义，三个正交属性（injection / ttl / writable_by），固定拼接顺序，每层预算 |
| `omni/memory.py` | 分层存储、TTL、会话绑定的一过性层、supersede、溯源、作用域过滤 |
| `omni/instructions.py` | 稳定头 + 易变尾的拼接、每层预算、**不变就不发 patch** |
| `omni/sidecar.py` | 快速文本模型判断要不要查 → 执行 → 产出「说的」和「显示的」两份结果 |
| `omni/realtime.py` | 事件解析、未知事件透传、ack 等待与超时兜底、**查询结果的三种合流方式** |
| `omni/extraction.py` | 会话结束时批量提炼，分配层和 TTL，拒绝写人格/规则层 |
| `omni/server.py` | aiohttp 入口、WS 端点、记忆读写 API（人格/规则层要人能看能改） |

**待做（阶段 1 剩余）**：

- [ ] **跑 E1**：复测记忆注入通道。这是唯一还能推翻现有架构的实验。
- [ ] **跑 E7**：`response.cancel` → `session.update` → `response.create` 的自打断时序在同一条连接上稳不稳。不稳就退到「说完再追加」这一种合流方式。
- [ ] **接上 workforce web 客户端**：客户端连 omni-server 而不是自己的 `server.py`；处理两个新事件 `omni.tool_result`（显示查询结果）和 `omni.interrupt`（丢掉已缓冲音频）。
- [ ] **端到端实测**：真实语音、真实记忆、真实查询，量首字延迟。
- [ ] **跑 E4**：注入长度 vs 首字延迟，把 `layers.py` 里的预算占位数字换成实测值。
- [ ] **存储落盘**。现在是进程内的，重启就没了。数据模型已经是可以直接落库的形状。

### 阶段 2：身份与多用户

- 身份体系（服务端 + 客户端，跨两个仓库）。
- 每用户一个 `MemoryStore` 作用域，配额与准入控制。
- **跑 E6**（并发压测）→ 拿到真实容量数字再定连接池策略。注意 E6 会把账号打进限流，单独安排一天。
- 语义检索（离线建索引，在线混合召回，50ms 预算内）。

### 阶段 3：群

- 群成员关系存真数据库（**不是 JSON**：并发写会静默丢更新，而且成员关系是权限判定依据，需要变更审计）。群配置可以是 JSON 一列。
- 群记忆写入路径。检索、作用域过滤、跨域不 supersede 已经就位并测过。
- 消息收件箱：未读、已读回执、按人分片投递。

### 阶段 4：路由（"我要跟A说话"）

排在群之后，因为它依赖两个上一阶段的产物：输出域过滤（`memory-design.md` §4）和封闭候选集（联系人/群成员列表）。这一阶段的重点全部是**防止发错**，不是功能本身：

- 收件人用拼音级模糊匹配打到封闭候选集上（热词在 ASR 层已实测不支持，只能事后纠偏）。
- 模式状态要有可见指示 + 明确的进入/退出确认；逃逸最好走物理按钮，不走语音。
- 逐字转发为默认；AI 代写必须在消息元数据里标出来。
- 撤回窗口（真撤回，不是标记）。
- 发送前用输出域过滤做最后一道检查。

### 阶段 5：更多服务端工具

文档知识库、分析类工具。工具接口（`omni/sidecar.py` 的 `Tool`）已经是稳定的形状，加工具不用动编排。注意读工具和写工具要分开对待——**绝不能让一次读工具的结果直接触发写工具**。

## 阶段 1 的验收标准

单用户、一条真实语音会话里能验证这几件事：

1. 人格层和规则层从头到尾逐字不变（抓 `session.update` 的 payload 对比）。
2. 连续两轮都没检索到记忆时，第二轮不发 `session.update`（省掉一次往返）。
3. 问一个需要查记录的问题：语音先说一句"我看看"，查询结果回来后自打断或追加，App 上同时出现结构化结果。
4. 说一句"接下来都简短点"，本次会话生效；**重开一次会话，它不在了**。
5. 会话结束后看提炼结果：层分对了，一过性内容没有进长期库，模型没能往人格/规则层写东西。
6. 首字延迟落在预算里（E4 给出的数字）。

## 测试纪律

workforce 的教训是限流窗口窄到"只够跑一次 5 轮的完整测试"。所以：

- **默认测试全部离线。** 现在 70 个测试跑 0.2 秒，不打任何上游。`tests/fakes.py` 里的 `FakeUpstream` 可以模拟 ack 丢失这种真实故障。
- **打真实上游的测试单独一组，需要显式开启**，CI 不跑。
- **E6 单独安排时间**，它会把账号打进限流。
