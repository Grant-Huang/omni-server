# 「三代纽带」架构框架

**这份文档是什么**：把产品设计方案（内部代号「三代纽带」，v0.1 草案）翻译成系统能力和组件——哪些是现有 omni-server 已经有的，哪些要新增，新增的东西怎么跟已有的分层记忆 / 作用域模型接起来，而不是另起一套。

**和其他四份文档的关系**：`design-risks-review.md` / `memory-design.md` / `architecture.md` / `roadmap.md` 描述的是 omni-server 作为通用多用户语音后端的样子；这份文档是**产品定了之后**的具体化——大部分设计可以直接复用，少数几处需要修订（identity 要接微信登录、群模型有一个比原计划更轻的先用版本），新增的部分（照片、生成式回忆、连接建议）原来的文档完全没覆盖。第 12 节列了对前四份文档的具体修订点，不用自己去 diff。

**读法建议**：第 1 节是结论，第 13 节是需要你确认的开放问题，这两节先看。中间是每个新增能力的具体设计。

---

## 1. 结论先行

- **omni-server 不是要重建，是要长出四个新模块**：媒体/生成管线、轻量版 family graph、连接建议引擎、Feed 排序服务。已有的分层记忆、作用域过滤、sidecar 查询模式全部保留、直接复用。
- **照片/故事/建议/Feed 不应该塞进 `MemoryEntry`**。`MemoryEntry` 的整个设计（层、注入时机、TTL）是为「进语音会话的 instructions」这一件事服务的；故事是要展示的富内容，建议是有生命周期的 UI 动作，Feed 是查询结果不是存储对象。硬塞进去会把已经测过的记忆模型搅浑。第 3 节展开。
- **Family Graph 的 MVP 需求比 `roadmap.md` 阶段 3 原计划的轻得多**——不需要消息收件箱/已读回执那套 IM 基础设施，只需要「一个家庭空间 + 成员角色 + 单条内容的参与者标签」。复用同一套 `group:` 作用域机制，不用等阶段 3 整体做完。第 4 节展开。
- **「连接」功能（AI 主动建议话题）需要语义检索**——这件事在 `memory-design.md` §10 里被列为「还没做」，产品方案的 MVP 直接依赖它，不能再往后拖。第 5 节给了 MVP 阶段一个足够用、不需要完整向量库的做法。
- **产品文档里有一处真实的自相矛盾，需要你来定**：价值观第 3 条和 V2 路线图都说「分享永远是老人主动选择，不会因为同一家庭空间被默认共享」；但 MVP 的 Feed 效果图里，「爸爸今天跟 AI 聊起了年轻时第一次买车」直接出现在家庭 Feed 里，没有经过任何「要不要分享」的动作。这两条现在对不上。第 5 节详细展开，第 13 节给了建议默认值，但这是产品对隐私的根本承诺，不该由我替你定。
- **原来讨论过的「语音路由」（"我要跟 A 说话"，`design-risks-review.md` 第 6 节）不在这个产品的 MVP 甚至 V2 范围内**。这个产品里语音只做两件事：老人对着 AI 说话（被记下来）、老人的极简语音优先交互。没有「AI 帮我把这句话转达给谁」这个功能。少了一大块要担心的东西，明确写下来，避免以后误建。

## 2. 能力地图

产品文档自己已经把 Family Memory Engine 拆成五个长期能力，并给了 MVP 范围——这个划分是对的，直接用它当骨架，不用另起一套分类法。

| 能力 | MVP 范围 | 落在哪个模块 | 状态 |
|---|---|---|---|
| Realtime AI | 语音采集/转写 | `omni/realtime.py` + `omni/upstream.py` | ✅ 已有，直接复用 |
| Generative AI | 照片 + 对话 → 故事/回忆片 | 新增 `omni/story.py`（第 7 节） | 🆕 新增 |
| Multimodal Memory | 照片 + 语音关联存储 | 新增 `omni/media.py` + 对象存储（第 3、11 节） | 🆕 新增 |
| Temporal Memory | 单事件起止时间 | 新增实体自带字段，不需要独立模块 | 🆕 新增（很薄） |
| Family Graph | 「这次事件谁在场」标签 | 复用 `memory.py` 的 `scope`/`disclosable`，新增极简成员表（第 4 节） | ♻️ 复用为主 |

产品的三个「魔法时刻」不是三个独立功能，是这五个能力的三种组合：

| 魔法时刻 | 用到的能力 |
|---|---|
| ① 看见（Family Feed） | Multimodal Memory（存）+ Family Graph（标签）+ Feed 排序（新，第 6 节） |
| ② 连接（AI 找话题） | Multimodal Memory（检索）+ 连接引擎（新，第 5 节）+ Realtime/文字消息投递 |
| ③ 传承（回忆片） | Generative AI（新，第 7 节）+ Multimodal Memory + Temporal Memory |

## 3. 新增核心实体：为什么不是 `MemoryEntry`

`MemoryEntry` 的设计前提是「这段内容要不要、什么时候进语音会话的 `instructions`」——层、注入时机（`always`/`retrieved`/`session`）、TTL 全部是围绕这一件事定的。产品新增的四类内容，没有一个是这个形状：

- **Story**（如「我们的东京 2027」）：有标题、多张照片、生成的叙事文字、日期范围、参与者。是**要被展示的富内容**，不是「要不要塞进 prompt 的一段文字」。
- **Suggestion**（如「爷爷也去过富士山，要不要问问他？」）：有生命周期（生成→展示→被点击→促成对话→过期/忽略），是**有状态的 UI 动作**，不是事实性记忆。
- **FeedItem**（Feed 里的一条）：是**查询结果**，不是独立存储的东西——它是对 Photo/Story/Suggestion/MemoryEntry 做排序后的视图，不应该有自己的写入路径（第 6 节展开）。
- **Photo**：原始媒体 + 元数据 + AI 生成的内容描述，是新的一类原始数据，跟"记忆"完全不同性质。

**结论：这四类内容各自建表/建 store，`MemoryEntry` 保持不变，只在需要"让语音会话知道这件事存在"的地方，由提炼流程生成一条**指向它们**的轻量记忆条目**——不是把 Story 整个塞进去，是像「5 月份一家人去了东京，生成了一段回忆」这样的摘要，附带 Story 的 id。这样语音对话能自然提到"你们上次东京之行"，但 Story 本身的展示走它自己的 API，不途经记忆分层逻辑。

草案字段（细化到实现时再定，这里定的是"属于哪张表、跟谁关联"这个形状）：

```
photos
  id            TEXT PK
  scope         TEXT        -- group:family_<id>，见第 4 节
  uploaded_by   TEXT        -- user id
  storage_key   TEXT        -- 对象存储里的 key，见第 11 节
  taken_at      REAL NULL
  caption_ai    TEXT NULL   -- VLM 生成的内容描述，连接引擎检索用（第 5 节）
  participants  TEXT[]      -- user id 数组，"这次事件谁在场"标签
  event_id      TEXT NULL   -- 关联哪个事件/故事，见下

stories
  id            TEXT PK
  scope         TEXT
  title         TEXT
  narrative     TEXT        -- AI 生成的叙事文字
  photo_ids     TEXT[]
  event_start   REAL
  event_end     REAL NULL
  participants  TEXT[]
  created_by    TEXT        -- human | generation（同 MemoryEntry 的 writable_by 精神，谁触发生成的）
  created_at    REAL

suggestions
  id              TEXT PK
  scope           TEXT           -- 通常是 group:family_<id>
  target_user     TEXT           -- 建议展示给谁
  subject_user    TEXT           -- 建议聊的对象是谁（爷爷）
  trigger_ref     TEXT           -- 触发这条建议的 photo/story id
  matched_ref     TEXT           -- 被匹配到的、属于 subject_user 的历史内容 id
  drafted_opener  TEXT           -- AI 起草的开场白
  state           TEXT           -- surfaced | opened | dismissed | expired
  created_at      REAL
  expires_at      REAL           -- 建议是有时效的，见第 5 节
```

## 4. Family Graph：阶段 3 群模型的一个更轻的子集，不是新设计

`roadmap.md` 阶段 3 原来设想的「群」是完整的多群聊场景——一个人可能同时在很多群里，需要未读/已读回执、按人分片投递的消息收件箱。那套是给"用户不选群，对统一 AI 说'我要在 BB 群跟 A 说话'"这个原始设想用的。

**这个产品用不到那一套。** 产品文档里没有"家庭群聊"这个功能——家庭成员之间的对话走的是各自的普通社交方式（AI 起草一句话，人自己去发），不是在 App 里有个消息收件箱。Family 在这个产品里只是一个**作用域边界 + 一组角色标签**，不是一个消息系统。

所以 MVP 需要的东西，是阶段 3 计划的一个严格子集：

```
families
  id            TEXT PK
  created_at    REAL

family_members
  family_id     TEXT REFERENCES families(id)
  user_id       TEXT REFERENCES users(id)
  role          TEXT        -- elder | parent | child
  joined_at     REAL
```

一个家庭 = 一个 `group:family_<id>` 作用域。已经写好并测过的 `disclosable()`（按输出目标过滤）、`forget_origin()`（退出级联失效）直接可用，不用改一行。

**不需要现在做的**：消息收件箱、未读/已读、按人分片投递——这些是阶段 3 原计划里为「群聊路由」设计的，这个产品不需要它们。等以后真的要做"家庭群聊"或者"AI 帮我在群里发消息"这类功能时再捡起来，届时阶段 3 的完整设计还在，不会因为先做了这个轻量版而作废。

**一个人属于几个家庭**：产品文档默认"一个家庭"，但现实里会有"我自己的小家 + 配偶那边的大家庭"这种情况。好消息是这个不需要现在决定——`disclosable()` 的 `memberships` 参数本来就是按"当前这个人属于哪些作用域"现算的列表，不是写死的单值，支持一个人属于多个 `group:family_*` 从第一天就是免费的，不用因为这个产品先做单家庭假设就把这条路堵死。

## 5. 连接引擎：需要语义检索，以及一处需要你来定的隐私边界

### 5.1 这是本文档里唯一需要新算法思路的部分

「连接」的流程（女儿传一张富士山照片 → AI 发现爷爷有相关记忆 → 主动建议）需要的能力，`memory-design.md` §10 早就点名过：

> 现在没有语义检索……omni-server 恰恰就是那个"该做这件事的地方"……但要注意它进关键路径。

之前是"以后要做但不阻塞"，现在产品的 MVP 核心场景直接依赖它，**语义检索从"待办"变成"阻塞项"**。

好消息是这里**不进对话关键路径**（不像语音会话那样要在 1 秒内出结果），连接建议是异步生成、下次打开 App 或者刷新 Feed 时才看到的，所以 MVP 不需要一上来就上完整的向量数据库 + ANN 索引这种重家伙：

- **MVP 做法**：新照片/新内容上传时，触发一次异步任务——用 VLM 生成内容描述（"日本富士山，秋天，逆光"），拿这段描述去跟同一个 family 作用域下其他成员的 Photo/Story 的 `caption_ai` 做一次 embedding 相似度检索（简单的 embedding API 调用 + 存量数据里做一次线性扫描或者用 SQLite 的一个扩展做近似检索，家庭规模的数据量——几百到几千条——线性扫描完全跑得动，不需要专门的向量数据库）。
- **命中阈值要严**：宁可错过一次建议，不要建议不相关的东西——错误建议比没有建议更伤这个产品想建立的"AI 真懂我们家"的印象。
- **V2 再考虑真正的向量索引**，如果家庭规模的数据量证明线性扫描不够用。

### 5.2 隐私边界：具体规则

产品价值观第 3 条说得很清楚：私聊内容归本人所有，不因为同一家庭空间被默认共享。落到连接引擎的具体规则应该是：

**连接引擎只检索 `scope = group:family_<id>` 的内容，从不检索 `scope = user:<id>` 的私人记忆——即使是同一家庭成员的私人记忆。**

这条规则要在检索这一步就生效，不是"检索到了但过滤掉"，是**私人内容从来不会被拿去建索引、参与匹配**。这样即使连接引擎有 bug，最坏结果也是"没找到该有的建议"，不会是"泄露了不该泄露的内容"——跟 `memory-design.md` §4 讨论群记忆泄露防线时的原则一致：防线要建在写入/索引侧，不能只指望检索时的判断。

这条规则要求家庭成员愿意"往家庭空间里放东西"（传照片到家庭相册、跟 AI 聊天时产出的内容进了家庭 Feed），连接引擎才有东西可匹配。这跟下面 §5.3 的矛盾直接相关。

### 5.3 产品文档里的一处矛盾，需要你来定

**矛盾具体是什么**：

- 价值观第 3 条："一个人和 AI 说的话归他自己所有，不会因为在同一个家庭空间就被默认共享。分享永远是主动选择，不是默认行为。"
- V2 路线图："老人与 AI 的私聊和家庭共享空间严格分离……分享永远是老人主动的选择。"（这条被列在 V2，暗示 MVP 阶段这个分离还不完善）
- 但 MVP 的 Family Feed 效果图里，"爸爸今天跟 AI 聊起了年轻时第一次买车"直接出现在家庭 Feed 里——这是老人跟 AI 的一段对话内容，没有任何"要不要分享"的动作就进了家庭可见的地方。

三选一，效果差异很大：

**方案 A：MVP 就默认私密，V2 才有共享**——老人跟 AI 的对话默认只存在 `user:<elder_id>` 作用域，Feed 里完全不出现这类内容，只出现照片和明确上传到家庭空间的东西。**代价**：MVP 效果图里最打动人的那条 Feed 内容（AI 从聊天里挖出爸爸的回忆）做不出来，"看见"这个支柱在 MVP 阶段会显得单薄很多。

**方案 B：MVP 阶段"提炼后的事实"默认进家庭空间，原话不进**——跟对话本身（可能涉及隐私的完整内容）留在私人作用域，但提炼流程（已有的 `Extractor` 模式）生成的、经过摘要的"值得让家人知道的一句话"默认写入 `group:family` 作用域。**代价**：默认行为本身就是"分享"，跟价值观第 3 条"分享永远是主动选择"字面上冲突，除非把这条理解成"分享具体的私密细节永远要问过"，摘要级别的"提到了什么"不算——这个界限需要你来画，不是我能替你决定的产品判断。

**方案 C：低摩擦的确认，不是完全默认，也不是完全手动**——AI 提炼出"这段值得让家人知道"的内容后，先问一句"要不要让家里人也看到这个？"，确认了才进家庭空间；对于明显中性、无隐私风险的内容（比如"提到了想去日本"这种），可以有一个"低风险自动过、高风险才问"的分级，但分级本身也是产品判断。**代价**：多一步交互，且"低风险自动过"这条本质上还是方案 B 的问题，只是缩小了范围。

**我的建议**：方案 C，且低风险自动过这条先不做（先做纯确认版），理由是价值观第 5 条"克制不打扰"和第 3 条"隐私是信任前提"都指向"宁可少一点自动化，也不要默认动作是分享"，MVP 阶段建议先用最保守的版本验证核心体验，效果图里的那条 Feed 内容可以晚一点上，不必须在第一版就有。但**这是对产品最根本的隐私承诺的具体化，应该由你确认，不该我替你定**。

## 6. Family Feed：这是排序问题，不是存储问题

"今天的家"这个默认视图，本质是"把 Photo / Story / Suggestion / 挑选出来的 MemoryEntry 摘要，按重要性排个序给中年人看"。

**不应该有一张 `feed_items` 表让各个模块往里写。** 理由和 `memory-design.md` §7.7 讨论检索时是同一个——source of truth 只应该有一处，Feed 是**读时计算/排序**的结果，不是**写时物化**的存储：

- Photo 上传、Story 生成、Suggestion 创建，各自写各自的表（第 3 节）。
- 请求 Feed 时（或者后台定期预计算缓存），拉取该家庭作用域下最近的 Photo/Story/Suggestion + 提炼流程标记为"值得家人知道"的 MemoryEntry 摘要，按新鲜度 + 重要性打分排序，拼成 Feed 返回。
- 打分逻辑一开始可以很简单（新鲜度 + 是否有未读 Suggestion 优先），不需要 MVP 就上复杂的排序模型。

好处：任何一个源头模块出 bug，不会污染一份独立的"Feed 真相"；调排序逻辑不用管数据怎么写进来的。

## 7. 生成管线（Story Composer）：复用 Extractor 的范式

生成一支「我们的东京 2027」，需要两次模型调用（VLM 理解照片 + 文本模型编排叙事），跟已有的 `Extractor`（`omni/extraction.py`）是同一类工作：**批处理、在关键路径之外、触发之后允许有延迟**。不需要新发明一套编排逻辑，照抄这个范式：

```
StoryComposer（新增 omni/story.py，形状对齐 Extractor）
  输入：一组 Photo + 关联的对话片段（同一事件参与者在这段时间跟 AI 说过的话）
  触发方式：
    - 显式请求（用户点"生成这次旅行的回忆"）
    - 事件边界检测（同一 event_id 下 N 天没有新内容，判定"这件事结束了"）
    - 节日节点（春节、生日——第 10 节的增长设计需要这个）
  产出：一条 stories 记录 + （可选）一条摘要性的 MemoryEntry，讲给语音会话听
  失败处理：跟 Extractor 一样——失败只丢这一次生成，不影响任何已经存在的数据，记日志不重试（MVP 阶段）
```

Vision 模型调用建议走跟现有文本 sidecar 同一个供应商（DashScope/百炼有 Qwen-VL 系列），保持"同一套账号、同一个区域"的约束不被打破（见第 11 节）。

## 8. 身份：微信登录怎么接到已有的自建身份设计上

产品文档要求「微信登录从第一天接入，账号锚定在微信 OpenID/UnionID」。这跟 `architecture.md` §2.3 已经定的"自建身份"决策**不冲突，是同一个决策的延伸**——"自建"说的是不复用 workforce/AgentNexus 的账号体系，不是说要自己做账号密码登录；微信只是换了一个身份验证的前门，后面的会话/token 机制不变。

对 §2.3 的具体修订：

```diff
 users
   id            TEXT PRIMARY KEY
   display_name  TEXT
   created_at    REAL
+  wechat_openid   TEXT UNIQUE   -- 同一微信开放平台账号下唯一
+  wechat_unionid  TEXT NULL     -- 跨应用统一标识，未来接小程序/分享通道时靠它认出同一个人
```

认证流程也要改一处：不再是"邀请码换 token"，是"微信 OAuth（App SDK 完成）→ 服务端拿 code 换 openid/unionid → 首次登录建 `users` 行 → 签发长期 token"，后面 token 怎么在 WS 握手时传、查询参数会进日志要脱敏——这些 §2.3 已经写清楚的部分不变。

**新增一步 §2.3 原来没有的**：家庭邀请流程。中年人（通常是第一个注册、第一个付费的人）生成邀请链接/二维码 → 父母/孩子扫码走微信登录 → 登录成功后，用邀请携带的 family_id 直接写入 `family_members`，不需要额外的"申请加入审核"这一步——产品定位是家庭内部工具，不是陌生人社交，邀请即信任。

**需要你确认的一件事（不阻塞设计，但阻塞开发排期）**：产品文档自己写了"移动应用微信登录历史上对主体资质有审核要求，需要现在就实际提交申请确认"——这是产品文档自己列的"待核实"风险项，我在这里重复一遍，因为它是身份设计能不能按这个方案走通的前提，建议现在就去申请核实，不要等开发到这一步才发现卡住。

## 9. 语音角色收窄：跟 `design-risks-review.md` 的关系

`design-risks-review.md` 第 6 节花了很大篇幅讨论"意图路由"——用户说"我要跟 A 说话"，AI 把话转达出去的风险（同音字纠错、模式错误、送达语义、跨群串味）。**这个产品完全不需要这套东西**：

- 语音在这个产品里只做两件事：老人对着 AI 说话被记下来（feeds Family Memory）；老人端的极简语音优先交互（大按钮）。
- "连接"功能里 AI 起草的开场白，是**推给人自己去发**（"AI 帮她开口"——女儿自己点、自己发），不是 AI 代替用户实时把语音转达给另一个人。
- 没有"群"这个用户要对话的对象概念（第 4 节已经说明这个产品的 family 只是作用域，不是聊天室）。

所以 `design-risks-review.md` 第 6 节全部内容（R5、拼音模糊匹配、逃逸词设计、撤回窗口等）**当前不需要实现**。不是被推翻，是这个产品的 MVP/V2 范围内用不上——如果以后产品方向扩展到"帮我把这句话转达给谁"，那部分设计还在，直接捡起来用。现在不建，避免为不存在的需求写代码。

## 11. 存储与部署：新增项

`architecture.md` §4 定的硬约束（cn-beijing、长驻进程）不变，新增：

- **对象存储**：照片原始文件不进 SQLite（不适合存二进制大文件）。需要一个 S3 兼容的对象存储，阿里云 OSS 是自然选择——跟已经确定的"cn-beijing 部署"、"DashScope 同区域"约束一致，不引入新的地域依赖。**这个不需要现在拍板具体服务商**，按 `architecture.md` 的既有原则——先把接口形状（上传/取 URL/删除）定成一个小接口，具体实现是可替换的一个模块，跟 `persistence.py` 之于 SQLite 是同一个思路。
- **VLM（图像理解）模型**：第 5、7 节都需要。建议同样走 DashScope/百炼（Qwen-VL 系列），保持"同一个账号、同一个区域、同一套配额"的既有约束，不引入第二个云服务商的依赖和第二套限流问题要踩坑。
- **数据量级重新评估**：原来的容量模型（`design-risks-review.md` §4）只算了语音连接的带宽/配额，现在要加上照片存储和 VLM 调用的量——但这些都不在实时语音的关键路径上，不会影响已经讨论过的语音延迟预算，是独立的一条容量曲线，MVP 阶段（几个家庭、几百张照片）用不着现在就精算。

## 14. 建议的实现顺序

对齐产品文档自己的阶段划分（MVP → 春节仪式 → V2），从工程角度排一下依赖：

1. **身份层**（第 8 节）——所有东西的前提，微信资质核实要最先启动（并行于开发）。
2. **Photo 存储 + Family Graph 最小版**（第 3、4 节）——没有这个，后面什么都做不了。
3. **Feed 排序服务的骨架**（第 6 节）——先能显示照片列表，验证"今天的家"这个视图的基本形态，不用等生成引擎和连接引擎完工。
4. **StoryComposer**（第 7 节）——传承支柱，复用 Extractor 范式，相对独立，可以跟第 5 步并行做。
5. **连接引擎**（第 5 节）——技术上最新、风险最高的一块，依赖 §5.3 的隐私边界先定下来，建议放在验证了前三步的基本体验之后再做，不要一开始就啃最难的骨头。
6. **春节增长设计**（产品文档第 10 节）——复用第 4 步的 StoryComposer，只是换一个触发时机（节日节点而不是用户手动请求），是运营配置，不是新的技术能力。
